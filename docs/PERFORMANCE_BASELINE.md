# Baseline производительности — 26.10.2026

Первые **измеренные** числа (раньше в [плане стабилизации](STABILIZATION_PLAN.md) §4 были только бюджеты). Это замеры на Windows, не на телефоне и не по реальной сети: они показывают стоимость самого клиента, а не канала.

## Среда

- Windows 11, сборка **Release** (MSVC 2022, `/O2`), Qt 6.12, libssh2 (master `6e7b207`) + OpenSSL 3.6.5.
- Сервер — одноразовый Debian 13 в WSL, подключение по loopback: задержка сети ≈ 0, поэтому SSH-числа — это цена протокола и криптографии, а не сети.
- Воспроизведение: `python tool/run_perf_baseline.py [--soak-minutes 5] [--entries 20000]` (поднимает каталог с файлами и одноразовый ключ, запускает `build-msvc/fortiq_perf.exe`, в конце всё убирает). Исходник замеров — [`tests/PerfBaseline.cpp`](../tests/PerfBaseline.cpp), в `ctest` не входит.
- Числа сняты на одной машине одним прогоном; разброс между прогонами не оценивался (где повторяли — указано).

## Найдено

1. **Терминал: слой экрана libvterm стоит ≈ 10 мкс на каждую прокрутку строки.** Разложение (`fortiq_perf vterm`): сам разборщик libvterm — **500–1100 МиБ/с**; слой экрана с отброшенной прокруткой — 9,4–9,9 мкс на строку; со складыванием в буфер прокрутки как в `TerminalView` — 13,7 мкс. То есть время уходит не в разбор и не в наш буфер прокрутки, а в перемещение содержимого экрана (≈ 40 × 150 ячеек) при каждой прокрутке. Следствие: до исправления одно чтение из SSH (до 64 КиБ строк по 2 байта = 32 000 прокруток) **блокировало окно на 0,3–0,45 с**, и так на каждом опросе, пока идёт поток.
   - **Исправлено (не оптимизацией libvterm, а режимом работы):** `TerminalView::feedLater()` разбирает байты кусками (≈ 8 мс работы за ход цикла событий, порядок сохраняется); пока в очереди больше 256 КиБ, окно просит контроллер **перестать читать** из SSH (`setBackpressure`, гистерезис до 64 КиБ). Удалённая программа блокируется на заполненном окне SSH, вывод не копится в памяти.
   - **Дополнительная находка при проверке:** когда читаешь не всё, **ввод тоже перестаёт доходить**: sshd не читает соединение, пока не может отдать накопленный вывод, и Ctrl+C не срабатывал (процесс `yes` оставался жить, пока чтение не возобновлялось). Исправлено: в режиме «не читать» клиент всё равно вынимает пакеты из сокета в собственную очередь libssh2 (`libssh2_poll`, размер ограничен окном канала), и Ctrl+C доходит.
   - **Проверено:** `TerminalSequencesTest::feedLaterGivesTheSameScreenAndKeepsTheLoopAlive` (тот же экран и та же прокрутка, что при синхронной подаче; самая длинная пауза цикла событий < 150 мс), `resetDropsTheBacklog`, живой `terminalBackpressureStopsReadingNotTyping` (под давлением читается ≤ 64 КиБ, `yes` на сервере жив и заблокирован, Ctrl+C его убивает, чтение возобновляется).
   - **Не исправлено:** потолок ≈ 100 000 прокрученных строк/с остался (нужна правка libvterm: кольцевой буфер строк экрана вместо `memmove`; это правка стороннего кода с риском, делать после накопления эталонных тестов эквивалентности).
2. **Files: каталог больше 20 000 записей открыть было нельзя вовсе — исправлено 26.10.2026.** Сессия читает каталог целиком (до `kMaxListedEntries` = 300 000) в компактном виде (≈ 150 байт на запись вместо `QVariantMap` из десяти ключей), сортирует (папки, затем имя) и отдаёт интерфейсу **первую страницу в 5000 записей**; `RemoteController` держит весь список и по «Afficher plus» (+5000) или «Tout afficher» (до 50 000 записей в интерфейсе) добавляет следующие страницы. Строка внизу окна показывает «N элементов из M»; фильтр работает только по уже показанным (об этом сказано в строке). Кэш назад/вперёд хранит только каталоги, влезающие в одну страницу. Не сделано: настоящая виртуализация модели (QML по-прежнему получает JS-массив), сохранение числа загруженных страниц при обновлении папки (после «Обновить» снова первая страница), потоковое чтение (каталог читается весь до показа первой страницы).
3. **Санитайзер HTML: ≈ 1,2 МБ/с** (3 МБ за 2,6 с; верхняя граница страницы Browser — 5 МБ, то есть до ≈ 4 с). В **Mail** он шёл в рабочем потоке, в **Browser** — в потоке интерфейса. **Исправлено 26.10.2026:** Browser декодирует и очищает страницу в рабочем потоке сразу после загрузки (`FetchOutcome::page`; если за это время изменились адрес или режим чтения, страница очищается заново), а переключение режима чтения идёт через `QtConcurrent` с отбрасыванием устаревших результатов (быстрое двойное переключение: побеждает последний выбор). Скорость самого санитайзера не менялась (ускорение разборщика не делалось); страница по-прежнему появляется через те же ≈ 2–4 с, но окно не замирает. Проверено живым `browser…` тестом (108 тестов Browser и 56 живых зелёные); замер «окно не замирает» на 3 МБ странице отдельно не снимался.
4. Подключение занимает ≈ 116 мс на loopback: для интерактивного ощущения нужно держать сессии постоянными (так и сделано), не переподключаться на каждое действие.

## Заодно найдено в стенде

Windows **перераспределяет зарезервированные диапазоны портов** (Hyper-V/WinNAT, `netsh int ipv4 show excludedportrange protocol=tcp`; сейчас, например, 2223–2322): порт внутри диапазона не пробрасывается из WSL на Windows. Из-за этого `obsoleteAlgorithmsAreRefused` внезапно стал красным («TCP-соединение невозможно»), хотя код не менялся. `tool/prepare_live_fixture.py` теперь выбирает блок из пяти портов, который Windows может занять (`FORTIQ_IT_WEAK_BASE`, по умолчанию 2431), и перед запуском проверяет, что нужные порты достижимы **с Windows**, а не только слушают в WSL. Полный живой прогон после этого и после правок терминала: `fortiq_ssh_it` 55 прошли, 0 красных, 1 пропуск (`twoHostsNeverMix`), `fortiq_publication` 49/49.

## Не измерено (честно)

Телефон и планшет; реальная сеть с потерями и задержками; часовой soak; время построения QML-сцен и переключения окон (5–10 открытых окон); сетка Files на 20 000 элементах; поток журнала 10 000 строк/с **через живое соединение** (измерен только разбор, не канал); Qt Quick Profiler / число элементов сцены.
