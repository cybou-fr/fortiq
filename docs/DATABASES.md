# Bases de données — SQLite и PostgreSQL, только чтение (первый срез, 23.10.2026)

Приложение — графический интерфейс к существующим `sqlite3` и `psql` на выбранном Linux-сервере. Клиент FORTIQ **не** подключается к базам напрямую:
запрос выполняется на сервере по SSH (PostgreSQL может быть и на другой машине — тогда к ней подключается `psql` с сервера). Собственных серверных
агентов нет. Исследование инструментов: [APPS_RESEARCH](APPS_RESEARCH.md).

## Что умеет

- **Профили подключений** привязаны к сохранённому SSH-серверу (видны только при подключении к нему). SQLite: абсолютный путь к файлу на сервере.
  PostgreSQL: хост (пусто = локальный сокет), порт, пользователь, база, пароль. Метаданные — в настройках клиента (`db/profiles`); **пароль — только в защищённом
  хранилище клиента** (Windows Credential Manager / Android Keystore, ключ `db-<id>`). Нет защищённого хранилища — пароль сохранить нельзя (явное сообщение, без запасного
  файла). При смене хоста/порта/пользователя/базы сохранённый пароль **стирается** (его нельзя отправить на новую цель). Удаление профиля или сервера удаляет и пароль.
- **Схема слева:** таблицы и представления с колонками, типами и «не NULL» (`sqlite_master` + `pragma_table_info`; `information_schema` для PostgreSQL); кнопка `⏵` подставляет
  `SELECT * FROM "…" LIMIT 100` (идентификаторы из базы всегда квотируются).
- **Редактор** (Ctrl+Entrée) и **таблица результата:** NULL показан курсивом «NULL» и отличается от пустой строки и текста «NULL»; числовые колонки выровнены вправо; многострочные
  значения показаны с «⏎»; ячейка ограничена 2000 символами.
- **Лимиты:** время (5/15/30/60/120 с) и число строк (100/500/1000/5000); вывод одного запуска ≤ 4 Мио. При превышении результат помечен «tronqué».
- Каждый запрос — **отменяемая задача TaskManager** (`dbQuery`); текст SQL в списке задач **не** показывается.

## Только чтение: слои защиты — это защита от случайности, не граница безопасности

1. **Сканер SQL до отправки** (плюс запрет известных опасных функций по имени вне строк и комментариев: `readfile`, `writefile`, `edit`, `load_extension`, `fsdir`; для PostgreSQL — `pg_terminate_backend`, `pg_reload_conf`, `set_config`, `pg_read_file`, `lo_*`, `dblink*` и др.) (`scanSql`/`readOnlyRefusal`): ровно один оператор (учитываются строки, `E'…'`, `$тег$…$тег$`, идентификаторы, вложенные комментарии PostgreSQL, `[…]` и
   «`…`» SQLite); первое слово только `SELECT/WITH/VALUES/TABLE/SHOW/EXPLAIN` (SQLite: `SELECT/WITH/VALUES/EXPLAIN/PRAGMA`); незакрытые кавычки и нулевой байт отклоняются.
   **Мета-команды отклоняются:** `\…` вне кавычек для psql и строки, начинающиеся с `.`, для sqlite3 — иначе `\!` и `.shell` исполнились бы как команды оболочки, потому что SQL идёт
   на stdin клиента.
2. **Опции клиента:** `sqlite3 -safe -readonly` (запись невозможна на уровне открытия файла; `-safe` отключает функции оболочки `writefile()`, `readfile()`, `edit()`, `load_extension()` — **аудит 23.10.2026 нашёл, что без него `SELECT writefile(…)` создаёт файл**; если `sqlite3` не поддерживает `-safe` (старше 3.31), запрос не выполняется вовсе); `psql` с `PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=… -c lock_timeout=3000 -c idle_in_transaction_session_timeout=…'`.
   `WITH x AS (INSERT …) SELECT …` проходит проверку слова, но сервер/клиент его отклоняет (проверено вживую).
3. **Тайм-аут снаружи:** `timeout -k 2 N` вокруг клиента (SQLite — на N секунд; psql — N+5 после серверного `statement_timeout`).

Пользователь PostgreSQL может выполнить `SET default_transaction_read_only = off` (сканер это не пропускает, но это не граница). **Для настоящей гарантии используйте
роль БД без прав записи.**

## Передача данных и секретов

SQL и пароль идут **внутри скрипта на stdin** (`sh -s`): SQL — в heredoc со случайным разделителем (если он встретился бы в SQL, скрипт не строится); пароль — переменной `PGPASSWORD`
внутри скрипта. Ни то ни другое не попадает в аргументы процессов (проверено вживую: во время `pg_sleep` на сервере в списке процессов пароля нет), не пишется в журналы и не
показывается в сообщениях об ошибках. NULL в PostgreSQL отличается от пустой строки через случайный маркер `-P null=<<FQ-NULL-…>>` (на каждый запрос новый).

## Реализация и проверки

`src/db/DbInfo` (сканер, профили, лимиты, сборка скриптов, разбор CSV psql и `.mode quote` sqlite3, схема, тексты ошибок), `src/db/DbController`, `qml/shell/DbWindow.qml`.

- `fortiq_db` (19 тестов): профили, сканер (строки, `E''`, долларовые кавычки, вложенные комментарии, мета-команды, пограничные случаи), отказы, лимиты, скрипты (нет пароля в командной
  строке, коллизия разделителя), CSV с NULL/кавычками/переводами строк/CRLF/обрезкой, quote-режим sqlite3 (BLOB, NULL против `'NULL'`), тексты отказов, схема.
- Живой тест `databaseAppIsReadOnlyAndBounded` (нужны `FORTIQ_IT_DB=1` и кластер PostgreSQL 17): SQLite и PostgreSQL, NULL/юникод, отказы без сети и без задач, `.shell`/`\!` не исполняются,
  `WITH … DELETE/INSERT` отклонены вторым слоем, лимит строк и тайм-аут, отмена, неверный пароль, пароль отсутствует в `ps`, очистка при отключении и удалении сервера.
- `fortiq_db` дополнен тестами оценки роли (ok / warning / danger / note / unknown, рецепт и квотирование идентификатора, скрипты — фиксированные запросы без записи).
- Живой тест `databaseRoleCheck` (`FORTIQ_IT_DB=1`; роли — `tool/setup_db_roles_fixture.sh` от root на одноразовом Debian): владелец таблиц → warning; роль только для чтения → ok; роль с `pg_read_server_files` → warning; с `pg_write_server_files` и суперпользователь → danger;
  профиль остаётся рабочим; роль только для чтения **действительно** не может писать при обычной сессии без опций FORTIQ (`permission denied`); неверный пароль — не «проверка не удалась», а понятная ошибка; SQLite — запись возможна → note, после `chmod 444` → ok; очистка при отключении.
- Layout-тест с подставным контроллером: список профилей, схема, Ctrl+Entrée, форма PostgreSQL, **полоса роли** (свёрнута, раскрыта с рецептом, ok, скрыта).

## Что может подключённая роль (аудит 23.10.2026, R4)

При каждом открытии профиля (после чтения схемы) FORTIQ **читает права роли** фиксированным запросом по каталогу (текст запроса не зависит от ввода пользователя; запрос идёт в той же сессии только для чтения) и показывает полосу под заголовком окна:

| Уровень | Когда | Что видит пользователь |
|---|---|---|
| `ok` | у роли нет прав записи (таблицы, схемы, роли) | тихая зелёная строка «aucun droit d'écriture visible» с оговоркой, что функции и расширения всё ещё могут иметь побочные эффекты |
| `note` | PostgreSQL: `bypassrls`; SQLite: файл доступен пользователю SSH на запись | синяя строка |
| `warning` | право `INSERT/UPDATE/DELETE/TRUNCATE` хотя бы на одной таблице или представлении; право создавать объекты в схеме или схемы в базе; `CREATEROLE`, `CREATEDB`, `REPLICATION`; членство в `pg_read_server_files`, `pg_signal_backend`, `pg_checkpoint`, `pg_maintain` | жёлтая строка, по щелчку — список прав и **рецепт роли только для чтения** |
| `danger` | суперпользователь; членство в `pg_write_server_files`, `pg_execute_server_program`, `pg_write_all_data` | красная строка, сразу раскрытая, с тем же рецептом |
| `unknown` | проверку не удалось выполнить (старый PostgreSQL, права на каталог) | серая строка «non vérifiés»; на работу не влияет |

Рецепт (`CREATE ROLE fortiq_ro … GRANT pg_read_all_data … default_transaction_read_only = on`; для PostgreSQL ≤ 14 — отзыв `CREATE` на схему `public` у `PUBLIC`) копируется кнопкой; **FORTIQ его никогда не выполняет**: роль создаёт администратор базы.
Имя базы из профиля вставляется как идентификатор в кавычках. Для SQLite проверяются права файла и каталога (`[ -w ]`, владелец, режим).
Проверка ничего не блокирует: предупреждение — информация, а не запрет; права `ok` она не гарантирует (мы не видим побочных эффектов функций и расширений), поэтому слова об этом входят в сообщение.

## Проверка слоёв (аудит 23.10.2026)

Живой тест `databaseAdversarialCorpus` прогоняет 88 враждебных запросов через настоящие `psql` и `sqlite3` на роли-**владельце** таблиц и убеждается, что не изменено ничего: строки, таблицы, роли, значение последовательности,
файл SQLite, команды и файлы на сервере (`refuse` — не отправлено; `fail` — отправлено и отклонено сервером, например `WITH … DELETE`, `SELECT INTO`, `nextval`, `FOR UPDATE`; `ok` — безвредное чтение).
Модульные тесты проверяют сканер на 40 000 случайных последовательностей. Это не доказательство безопасности: **единственная настоящая гарантия — роль БД без прав записи и без прав на файлы/расширения.**

## Не сделано

MariaDB/MySQL (`--xml` проверен в исследовании), запись и DDL (потребуют отдельного режима с подтверждением), экспорт результата в Files, история запросов, подсветка SQL,
SSL-параметры подключения (используются настройки `psql` по умолчанию), BLOB-просмотр, пользовательские схемы поиска (`search_path`). Android на устройстве не проверялся.
