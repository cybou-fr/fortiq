## 1. Назначение и принципы

FORTIQ — Distributed Desktop Software: **только GUI-слой визуализации**.
**Linux — единственный backend** для хранения рабочих данных, серверных
настроек и всех доменных вычислений. Все 12 инструментов используют
предпочтительно **уже существующие зрелые CLI Linux по SSH**. Клиент
делает только отображение, ввод, необходимую UI-декодировку, минимальный
bootstrap SSH и отдельное лицензирование Lemon Squeezy; нет локальной
постоянной базы рабочих данных, независимых движков и самописного backend
по умолчанию.
Полная формулировка продукта и правила набора — в PRODUCT_SCOPE.

- Развитие идёт параллельно по рабочим приложениям, данным и управлению системой,
  когда готовы общие зависимости. Состав этапа определяется законченными сценариями.
- R0 готовит платный выпуск Windows с Lemon Squeezy и устраняет риски операций/соединений; R1 доводит Linux-инструменты;
  R2 добавляет полноценную почту и повседневные документы. Почта не блокирует R1.
- «Реализовано в коде» не означает «проверено» или «доступно в выпуске».
- Ресурсы, задачи, черновики и действия общие; переключение сервера не переносит операции.
- Все предметные операции проходят SSH exec/shell/PTY/SFTP/forwarding к серверным CLI.
  **Прямые SMTP/IMAP/HTTP/FTP подключения рабочих приложений Flutter запрещены.**
  Browser использует SSH SOCKS forwarding (`sshd` на сервере), без direct fallback.
- Встроенные приложения, порталы в браузере и удалённые GUI — разные возможности.
- Windows — основная платформа; наличие Android/iOS-папки не подтверждает поддержку.

### Жёсткая архитектура и безопасность хранения

**Linux исполняет весь доменный код и хранит все рабочие данные, настройки,
задачи, постоянные черновики и WorkspaceState.** Flutter — представление,
ввод, минимальный SSH-bootstrap и лицензирование. Только SSH: команды,
PTY, SFTP и forwarding. Любые настройки/установки Linux происходят **на
сервере** через существующие CLI. Свои серверные движки по умолчанию
не пишем — преимущество проекта в скорости интеграции зрелых Linux-программ.

**Позже, не сейчас:** надёжное шифрование серверных данных и настроек **at rest**
на Linux. Требования к управлению ключами/восстановлению будут утверждены
отдельно. Пока обеспечиваем SSH транспорт и безопасный вызов команд.
Менять SSH на более сложный транспорт без доказанной необходимости не планируем.

**Future-only security requirement:** SERVER-ENC-FUTURE — Linux-native
шифрование рабочих данных и серверных настроек **at rest** с отдельно
согласуемыми ключами и восстановлением. Статус: идея/требование на будущее,
**не включено в R0–R2**, не является критерием текущей готовности. SSH
остаётся текущим защищённым транспортом; переход на другой не планируется
без доказанной необходимости.

## 3. Общие задачи и зависимости

Все изменения ниже запланированы, если отдельное свидетельство реализации не
указано в §2. P0 — блокирует безопасную основу; P1 — необходим для сценария этапа;
P2 — расширяет подтверждённую основу. R0/R2 означает ранний контракт и позднюю
полную интеграцию, а не два разных CORE.

|---|---|---|---|---|

RemoteShell и будущие адаптеры. CORE-10/11 закрепляют требования поверх уже
имеющихся механизмов, не объявляя каждый дефект новой самостоятельной задачей.

Это **отдельный коммерческий контур**, его задачи не заменяют ни одно приложение APP.
Intro и Pro дают одинаковый полный функционал. [Контракт лицензии](LICENSING.md).

**Неопределённые коммерческие параметры:** необходимость контроля повторной покупки Intro, идентификация покупателя,
допустимое количество устройств, офлайн-период, политика отзыва, способ распространения.
До реализации они должны быть утверждены, а не назначены автоматически.

**Промокоды:** встроенные Discounts Lemon Squeezy — только необязательные
маркетинговые акции **Pro**, не третий тариф и не отдельный модуль.
По умолчанию скидка на первый годовой платёж, продление по 39,90 €;
лимит активаций кода, срок кампании и ограничение по продукту задаются
в Lemon Squeezy. На Intro скидки не действуют. Дополнительная разработка
механизма промокодов в R0 не требуется; перед акцией протестировать
покупку и стоимость будущего продления.

**UX-гипотеза для пилота, не SLA:** целевое время **до первого полезного
действия — три минуты после успешного SSH-подключения и необходимых безопасных
шагов Server Setup** на поддерживаемом тестовом Linux-хосте. Время платежа,
получения ключа, установки ПО и автоматических изменений системы в эту
метрику не прячем: записываем **отдельно**. Сравниваем с привычным способом
выполнить **ту же задачу**, не с вымышленным бенчмарком.

**Экспериментальная цель пилота, а не обязательный KPI релиза:** примерно
20 реальных покупок Intro и первые пять покупок Pro. При малой выборке
не делать вывод о рынке по одной доле конверсии. Долю
`Intro → Pro` считать только среди покупателей Intro, у которых **истекли
14 дней** и прошло согласованное окно для покупки Pro (например, ещё
14 дней), с указанием размера когорты. Повторные покупки и отмены учитывать
отдельно. Продление годовой подписки можно оценивать лишь после достаточного
периода продаж, **не** в первом двухнедельном пилоте.

**Измерения без нового backend:** заказы, сроки и оплаченные Pro брать из
Lemon Squeezy; первое действие/время выполнения/помехи фиксировать на
добровольных пользовательских сессиях или из обезличенных ручных отчётов.
Не добавлять прямой аналитический HTTP SDK в Flutter, не собирать SSH-ключи,
команды, адреса хостов, содержимое логов и файлов. Любая будущая продуктовая
телеметрия требует отдельного решения, прозрачности и проверки RGPD.

**Правило очередности:** R0 (платежи + безопасное подключение) не заменяется
другим релизом; в R1 завершение VALUE-02/03/04 важнее новых разрозненных
окон. R2–R4 не отменяются, параллельная работа допустима по готовым
зависимостям; функция считается коммерчески полезной только после
проверенного сценария, а не по факту существования GUI.

## 4. Матрица приложений

**Правило приёмки:** любая APP-функция имеет серверный console executable,
проверяемый `command -v`/версией, доставляемый/обновляемый при необходимости
через SSH. Источником действий служит Linux, а не Flutter.
Проверенная таблица 14 APP и конкретных CLI:
[SSH_FRONTEND_CONTRACT.md](SSH_FRONTEND_CONTRACT.md).
Без SSH допустимы только оболочка/минимальный bootstrap/покупка/лицензия
и RAM-буфер несохранённого ввода. Сервер хранит рабочие настройки, файлы,
постоянные черновики, историю и WorkspaceState, выполняет вычисления.
Mail всегда серверный CLI, прямой SMTP запрещён.

### APP-13 — Диски

### APP-14 — Состояние и подготовка сервера

- **Основная очередь:** R0 — подготовка и защита сервера при подключении, видимая пользователю, с откатом при потере доступа.
- **Статус:** существующая основа реализована в коде; перечисленные изменения запланированы, приёмка не зафиксирована.

- **Код:** `lib/services/server_setup_service.dart`, `lib/widgets/server_status.dart`; индикатор интегрируется в оболочку.
- **Сейчас:** Debian/Ubuntu. При подключении `inspect()` только читает (ОС, права, пакеты, обновления, unattended-upgrades, fail2ban, sshd, ufw, слушающие порты). Если есть что делать, открывается модальное окно, и `run()` выполняет шаги по порядку: пакеты Fortiq (tmux, procps, iproute2); `apt-get upgrade`; unattended-upgrades; fail2ban (SSH-jail, адрес клиента не банится); защита SSH (drop-in `00-fortiq-hardening.conf`: без паролей, root только по ключу; `sshd -t` до reload; только при входе по ключу); ufw (deny incoming, открыты SSH и все сейчас слушающие TCP/UDP-порты, чтобы не отрезать работающие службы). После SSH и ufw выполняется второй вход новым соединением; при неудаче изменение откатывается. Первая ошибка останавливает цепочку; «Stop after this step»; обрыв посреди шага — unknown.
- **Ближайший шаг:** прогон на disposable VM (root, sudo без пароля, без sudo; обрыв сети посреди шага), история шагов, повторная проверка после обрыва (unknown), блокировка apt, общий сервис возможностей хоста.
- **Бизнес:** объяснение «почему приложение недоступно» и состояние рабочей среды.
- **Администрирование:** обновления, требование перезагрузки, журнал шагов, защита SSH и файрвол.
- **Зависимости:** CORE-04/07/10/11; общий механизм задач (unknown) и второй вход из SSH-транспорта.
- **Готовность:** подготовка видна в окне с логом; после потери входа SSH/файрвол возвращаются в прежнее состояние (на VM); занятый apt не вызывает дублирующую операцию (Dpkg::Lock::Timeout); смена сервера не переносит задачу; не-Debian система и пользователь без прав получают понятный статус, ничего не меняется; вход по паролю не включает шаг SSH.

- Первый запуск после подключения и нужной проверки/подготовки Linux показывает

  обхода проверки SSH/UFW. Для пилота фиксируется время до первой полезной операции.
- Подготовка при подключении видна (окно с шагами и логом); шаги SSH и файрвола
  проверяются вторым входом и откатываются, шаг SSH недоступен при входе по паролю;

  одной сессии; поздний клиент освобождается, изменившийся ключ останавливает повторы.
- Разрыв SSH не скрывает результат опасной операции: unknown виден пользователю,

- Согласованы ResourceLocation/AppDescriptor/TaskManager; существующие окна доступны.
- Для каждого APP-01…14 зафиксированы уже существующая Linux CLI, package/capability и SSH-вызов; нет прямых протоколов и клиентских вычислительных backend.
- SOCKS проверен для HTTP/DNS/внутренних адресов/WebRTC и отказа без прямого fallback.
- Статический анализ и автоматические тесты проходят в CI с доступным отчётом.

### R1 — критерии приёмки

- Каждый рабочий ресурс и account привязаны к `serverId`, SSH-сессии и CLI; переключение не переносит действия. Local допустим только для UI/защиты черновика.
- SFTP-передача показывает прогресс, отмену по возможностям, ошибку и целевой источник;
  имена с пробелами, кавычками и Unicode не искажаются.
- Терминал присоединяется к своей tmux-сессии после reconnect; без tmux отсутствие
  сохранения объясняется, терминал открывается в выбранном каталоге.
- Конфигурация Linux не перезаписывается молча при конфликте; постоянный черновик Editor сохраняется и восстанавливается **на сервере через SSH**, ввод в RAM остаётся dirty во время save.
- Files → Editor → diff → save → verify сохраняет serverId, путь и версию;
  пользователь видит прогресс, конфликт или подтверждённый результат.
- Services → Logs → Editor → Restart → Verify выполняется на правильном сервере;
  неудачная запись блокирует restart; типизированная проверка конфигурации
  запускается на Linux при наличии подходящей CLI; результат повторно проверяется.
- При ожидании длительного SSH-действия GUI показывает реальное состояние
  задачи и безопасный следующий шаг; один курсор не заменяет статус.
- Процессы, TCP/UDP и журнал дают корректный контекст, SIGTERM отделён от SIGKILL.
- Диски доступны для просмотра; частичный анализ и недостаточные права отмечены;
  UFW проверяется на VM с сохранением SSH-доступа. Операций с разделами в R1 нет.

### R2 — критерии приёмки

- Документ, постоянный черновик и сохранённые параметры рабочего пространства восстанавливаются **с Linux-сервера по SSH** после перезапуска GUI.
- Серверный Mail CLI читает/отправляет через SSH на выбранном Linux; никакого SMTP/IMAP из Flutter. Без SSH нет синхронизации и отправки; несохранённый текст только в RAM, постоянный черновик — Linux.
- MIME-вложения открываются в Viewer (включая PDF), сохраняются в выбранный ресурс;
  письмо не отправляется повторно из-за ошибки сохранения отправленной копии.
- Общий поиск выполняется серверным `find`/`grep`/`rg`/`fortiq-search` по SSH, возвращает serverId и правильную строку.
- Workspace восстанавливает окна, источники и контекст без секретов и повторения команд;
  недоступный сервер не мешает экрану подключения/лицензирования и просмотру
  несохранённого RAM-ввода, но **ни одна рабочая операция не выполняется без SSH**.

### R3 — критерии приёмки

- Два сервера имеют независимые сессии, задачи, терминалы и контексты; переключение
  не меняет источник уже запущенного действия.
- Уведомления и история открывают правильные ресурсы и не содержат секретов.
- Выбранная конфигурация копируется, восстанавливается и проверяется на VM;
  неизвестный результат восстановления не приводит к автоматическому повтору.
- Решение по Containers/Jobs оформлено проверенным сценарием либо отложено явно.
  Несколько почтовых аккаунтов/OAuth, корзина и монтирование принимаются отдельно,
  если включены в конкретную поставку; не подменяют обязательные результаты.

### R4 — критерии приёмки

- Дисковые изменения проверены на образах/disposable VM: устройство повторно
  идентифицируется, системные и занятые устройства защищены, план и журнал видны.
- После разрыва результат разметки/форматирования проверяется без слепого повтора.
- Расширенные медиа проверяют большой файл, поток, буфер и ошибку; состав форматов
  и платформ подтверждён реальными испытаниями, а не наличием пакета.
- Дополнительная платформа получает свой отчёт о сценариях и ограничениях;
  не наследует статус Windows.

Для оценки коммерческого UX дополнительно использовать VALUE-01…06 и FLOW-11/12:
это **сценарии пилота**, а не утверждение существования результатов и не новая
продуктовая подсистема. Сначала проверяем функциональную готовность и
безопасность, затем наблюдаем поведение добровольцев и оплаченные конверсии.

В R0 дополнительно проверяются платежи Intro/Pro (FLOW-08/09), отзыв/отмена, откат SSH/файрвола, гонки reconnect,
смена host key и результат прерванных save/apt/restart. Приёмка связана с CORE-10/11/12 и LIC-01…07. Приёмка R1 начинается с FLOW-03/04/05, R2 — с FLOW-01/02/07
и полного FLOW-06.


## 7. Качество, границы и первые задачи

| Тип проверки | Обязательная область | Свидетельство |

## 8. Как поддерживать матрицу

Разделение ответственности: README — текущее поведение/запуск; PRODUCT_SCOPE —
что и зачем; ARCHITECTURE — как взаимодействовать; матрица — что, когда и как проверить.
Краткая дорожная карта README следует §5, не ведёт независимый подробный план.

После изменения обновлять исходное состояние и оставшиеся ограничения APP/CORE.
Использовать статусы «запланировано», «в работе», «реализовано в коде», «проверено»,
«доступно в выпуске». Для повышения статуса указывать коммит, окружение, дату,
сценарий и результат. Ссылка на метод или наличие кнопки недостаточны.

Приёмка фиксируется по FLOW и критериям этапа: пройдено / не пройдено / не проверено
с доказательством. Сейчас критерии §5 — предложения для реализации, не галочки
готовности. После выпуска обновлять README только подтверждёнными возможностями.
Если документы копируются в `www/assets`, обновлять эти снимки отдельно при
обновлении сайта; они не становятся самостоятельным источником плана.
