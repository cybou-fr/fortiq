# Аудит архитектуры и надёжности — Architecture & Reliability Gate (23.10.2026)

Основание: задание «Architecture & Consistency Gate / Core Reliability Gate» (внешний анализ репозитория на коммите `7e0ca60`). Работа выполнена на `main`, без веток и PR, без новых приложений и без изменения
принятой архитектуры («Qt GUI → SSH → существующие Linux-инструменты»). Анализ был сделан до срезов Courrier 2 и 3: **отправка почты, мастер аккаунта и вложения уже реализованы** ([MAIL](MAIL.md)); устаревшие
утверждения README/ROADMAP исправлены (раздел 7).

Что считается доказательством: **автоматический тест, который запускался и прошёл на указанном окружении**. Документация и юнит-тест без отказов не считаются приёмкой приложения. Пропуски перечислены отдельно и **не** считаются
пройденными. Окружение — одноразовый Debian 13 в WSL (`fortiq-test`: sshd, PostgreSQL 17, notmuch 0.39, isync, msmtp, dovecot, SMTP-приёмник `tests/fixtures/mail/smtp_sink.py`) и Windows 11 / MSVC 2022 / Qt 6.12.
Воспроизведение одним запуском: `python tool/prepare_live_fixture.py` (поднимает все фикстуры в одноразовом WSL, создаёт одноразовые ключ и пароль, запускает `tool/run_live_tests.py`, в конце убирает ключ и вспомогательные службы; шаг 2 плана стабилизации). Отдельные скрипты `tool/setup_*.sh` по-прежнему можно запускать вручную.

## 2. Матрица гарантий (инварианты)

| Инвариант | Чем проверен | Вердикт |
|---|---|---|
| Результат операции сервера A не попадает в контекст сервера B | `reliabilityInvariants`: запрос БД с `pg_sleep(3)` пережил смену сессии — после отключения и входа на «B» таблица, ошибка и выбор пусты, профиль виден только на «A», после возврата на «A» всё работает; те же проверки для Système, Réseau и Courrier (чтение, ответы приходят в закрытую сессию); для Files, Terminal, Disks и MDok — существующие тесты отключения и смены сессии | **подтверждён тестами** для Bases, Système, Réseau, Courrier, Files, Terminal, Disks, MDok; для Logs и Navigateur — **только по коду** (защита по поколению есть, отдельного живого теста нет). Оговорка: «A» и «B» — два профиля одного тестового хоста (разные поколения сессии), двух разных хостов в тестах нет |
| Неподтверждённая запись не повторяется, исход — `unknown` | `fortiq_publication` (28; `readBackMismatchIsUnknown`, отказы на каждом шаге публикации, конкурентные правки, отмена); `reliabilityInvariants`: отправка письма при обрыве SSH → задача `unknown`, статус «on ne sait pas», сохраняется после повторного входа; приёмник **получил** письмо (1), клиент не повторял (проверено 3 с спустя) | **подтверждён** для файловой публикации и отправки почты |
| Секреты не лежат открытым текстом на клиенте | `CredentialsTest` (Credential Manager, жизненный цикл); `reliabilityInvariants` §5: ни один ключ `QSettings` не содержит пароль БД/SSH/почты; пароль БД удаляется вместе с сервером; в `src` нет `qDebug/qWarning/std::cout` (секреты нельзя вывести в журнал) | **подтверждён** на Windows. Android Keystore — только эмулятор в раннем срезе. На сервере пароли почты лежат в файлах 0600 по решению владельца (R3) |
| Выход не теряет черновик молча и не обрывает работу без вопроса | layout-тесты (`allowAppClose`, диалог MDok; **диалог `SessionGuard`**: выход, кнопка «Se déconnecter», смена сервера, закрытие окна и Back при идущей записи — вопрос, «Attendre» ничего не меняет, «… quand même» завершает сессию; чтение и «живой» просмотр не спрашивают); `markdownDocumentsRoundTripConflictAndDisconnect`; `everyAppReportsItsWorkToTheTaskManager` (`guardingCount`) | **подтверждён** (backlog 1 закрыт 23.10.2026) |
| SQL не получает права записи | три слоя (сканер, `sqlite3 -safe -readonly`, read-only сессия `psql`) + корпус из 88 запросов на роли-владельце таблиц: ни строки, таблицы, роли, значения последовательности, ни файла/команды на сервере не изменено | **подтверждён как защита от случайности** после исправления D1/D2. **Не граница безопасности**: для гарантии нужна роль БД без прав записи (проверка роли приложением — в бэклоге) |
| HTML не исполняет активное содержимое | `structuredAttacksProduceOnlyTheAllowedGrammar` (4000 структурных атак: каждый выходной тег из белого списка, атрибуты только `href` http(s)/`colspan`/`rowspan`/`start`), `survivesRandomGarbage` (3000), письмо только с HTML | **подтверждён тестами свойств**; настоящего фаззера (libFuzzer/AFL) нет |
| Парсеры устойчивы к враждебному выводу сервера | случайные/усечённые/мутированные входы: CSV psql, quote-режим sqlite3, JSON notmuch (4 фикстуры × 600 мутаций, глубина 5000) | **подтверждён** (нет падений, инварианты формы) |
| Изменение почты (теги) согласовано с ответом | `reliabilityInvariants` §4: индекс только для чтения → тег не изменён, локальные теги и счётчики те же, сообщение «Étiquette non modifiée»; после восстановления работает | **подтверждён** |
| Задачи корректно переживают отмену | `fortiq_tasks` (21: флаги `guards`/`session`/`transient`), `everyAppReportsItsWorkToTheTaskManager`: Disks, Logs (чтения и «suivi»), MDok (открытие, сохранение, конфликт, копия) и Terminal (закрытие, отмена из панели, выход оболочки, обрыв связи → «cancelled», не «unknown») отчитываются в TaskManager; отмена пинга/поиска/релева/запроса БД в живых тестах | **подтверждён** для всех приложений, выполняющих работу на сервере (Système читает без задач: быстрое чтение, `session`-семантика не нужна) |
| Состояние после переподключения | `reliabilityInvariants` §1 (профили БД и работа после возврата), `mailSendAndWizard` (очистка при отключении) | **подтверждён**; автоматического переподключения в продукте нет |
| UI соответствует эталону | layout-тесты проверяют геометрию и поведение, не внешний вид | **не проверено** (визуальная приёмка открыта, [SHELL_FIDELITY](SHELL_FIDELITY.md)) |

## 3. Найденные дефекты

| № | Серьёзность | Дефект | Доказательство | Состояние |
|---|---|---|---|---|
| D1 | **P0** | `sqlite3` как оболочка даёт SQL-функции `writefile()`, `readfile()`, `edit()`, `load_extension()`, `fsdir()`. Они проходили проверку первого слова, а `-readonly` защищает только файл БД. `SELECT writefile('/tmp/x','pwned')` **создавал файл**, `edit('x','cmd')` запускает программу, `readfile` читает любые файлы пользователя | воспроизведено на sqlite3 3.46.1 (с `-safe` — «cannot use … in safe mode») | **исправлено**: `-safe` во всех запусках; если `sqlite3 -safe` не поддерживается (старше 3.31) — **отказ без запуска**; плюс запрет функций сканером; тесты `shellFunctionsAreRefused`, корпус, имитация старого sqlite3 |
| D2 | P1 | PostgreSQL: функции с побочными эффектами (`pg_terminate_backend`, `pg_reload_conf`, `set_config`, `lo_*`, `pg_read_file`, `dblink*`, …) проходили сканер | анализ (не воспроизводилось: нужны права роли) | **исправлено** запретом по именам идентификаторов (вне строк и комментариев); корпус |
| D3 | P1 | Мастер аккаунта: резервная копия существующего конфига сохраняла старый режим (например 0644) со старыми паролями, а сам файл становился 0600 | анализ скрипта | **исправлено** (`chmod 600` копии), проверено живым тестом |
| D4 | P1 | Вложения писались в `~/Downloads` с правами 0644: чужие локальные пользователи могли читать личную почту | анализ скрипта | **исправлено** (`umask 077`, 0600), тест |
| D5 | P1 | Прерванная отправка после повторного входа превращалась в «чистое» состояние, предупреждение о неизвестном исходе пропадало | `reliabilityInvariants` (упал до исправления) | **исправлено**: «неизвестно» держится до подтверждения пользователем; доказано, что письмо в таком случае **реально доставляется** |
| D6 | P2 | Разбор CSV/quote: строка длиннее заголовка давала лишние ячейки (сдвиг таблицы) | фаззинг `parsersSurviveRandomOutput` | **исправлено** |
| D7 | P2 | Адрес получателя мог начинаться с `-` (урок прототипа в DEVELOPMENT_MATRIX) | сверка с уроками | **исправлено** (`--` уже стоял; добавлен отказ) |
| D8 | P2 | Профиль БД: при сохранении нового профиля под его именем оставались строки, схема и результаты **предыдущего** профиля (выявлено тестом проверки роли) | `databaseRoleCheck` упал до исправления | **исправлено**: любое сохранение профиля сбрасывает состояние сессии; тест |

Тесты и фиксации: D5 и D6 — тест упал до исправления и проходит после; D1 — дефект воспроизведён вручную на sqlite3 до исправления, тесты (`shellFunctionsAreRefused`, корпус, имитация старого sqlite3) написаны вместе с исправлением; D2, D3, D4, D7 — проверка содержимого скриптов и живое подтверждение после исправления (до исправления не запускались).
