### Результат S-4 (24.10.2026): операция → поведение при отказе

Три отказа, которые клиент не отличает от успеха: **1** сервер отказал (ошибка протокола, ничего не сделано), **2** запрос потерян (ничего не сделано, обрыв), **3** подтверждение потеряно (сервер **выполнил**, клиент видит обрыв). Правила: отказ — обычная ошибка, сессия жива; обрыв — код `unknown`, сессия закрыта, **операция не повторяется** (одна попытка).

### Результат S-2 (25.10.2026): зависшая серверная команда

**Было (по коду и по прогону):** `SshSession::runScript` крутил цикл чтения без общего срока — команда, которая не завершается (`sleep`, зависший сетевой диск, заблокированная база), навсегда занимала единственный рабочий поток контроллера; вызовы без `keepGoing` (Logs, история Terminal, часть Mail) нельзя было прервать вообще. Отмена и обрезка по лимиту вывода закрывали канал, но **команда продолжала работать на сервере** (в отладочном прогоне процесс `sleep` пережил закрытие канала).

**Стало:**
- у `runScript` есть срок: параметр `timeoutMs`, по умолчанию 10 минут на сессию (`setCommandTimeout`); по истечении — `Error`, код `timeout`, уже полученный вывод сохраняется, сессия остаётся рабочей;
- при сроке, отмене и обрезке по лимиту вывода команда останавливается **на сервере**: запускается как `sh -s fortiq-run-<токен>`, вторая сессия находит процесс по токену (`pgrep`) и посылает TERM, через секунду KILL всей группе процессов (sshd делает `setsid`), так что дочерние процессы уходят вместе с ней; без `pgrep`/`ps` остановка не выполняется (best effort), срок на клиенте всё равно действует;
- ошибка, найденная при отладке: `kill -TERM -- -PGID` в dash молча не работает, нужен `kill -s TERM -- -PGID`.

Тест `hungServerCommandIsStopped` (5 сценариев, считает процессы `sleep` с уникальной длительностью на сервере): срок сессии, срок вызова (быстрая команда не страдает), отмена, обрезка по лимиту при `yes`, дочерние процессы. Регрессия: `fortiq_publication` 49, юнит-наборы (db 28, mail 15, mailsend 20, browser 108, network 14, system 12, logs 11), живые Mail/DB/System/Network/TaskManager тесты `fortiq_ssh_it` проходят. В полном прогоне `fortiq_ssh_it` 5 тестов были красными из-за окружения (нет SMTP-приёмника после перезапуска WSL, вход по ключу вместо пароля для двух тестов); после запуска `setup_mail_live_fixture.sh` почтовые тесты проходят.

**Не покрыто / остаток:** срок 10 минут общий — для известных долгих операций (первая синхронизация почты) его нужно будет увеличивать явным `timeoutMs`; сообщение о сроке пока не доведено до статуса задачи в UI отдельным текстом (приложения показывают его как ошибку команды); `pgrep`/`ps` обязательны для остановки на сервере; SFTP-операции (листинг, передача) имеют собственный тайм-аут сессии 15 с и этим тестом не затронуты; Android.

### Результат S-1 (25.10.2026): набор алгоритмов SSH

**Было:** клиент не задавал `libssh2_session_method_pref`; тест показал, что сервер, предлагающий только обмен ключами `diffie-hellman-group14-sha1`, принимался (клиент доходил до вопроса о доверии к отпечатку).

**Стало** ([SshSession.cpp](../src/ssh/SshSession.cpp)): перед рукопожатием из списка алгоритмов самой libssh2 (в её порядке) убираются устаревшие: обмен ключами с SHA-1 и `group1`, ключи хоста `ssh-rsa` (SHA-1) и DSA, шифры CBC/3DES/RC4/Blowfish/CAST, MAC на MD5/SHA-1, «none». Порядок сохранён намеренно: тип согласуемого ключа хоста не меняется, поэтому уже сохранённые отпечатки не ломаются (проверено: обычный сервер даёт тот же отпечаток, что был закреплён). При отказе показывается понятное сообщение (серверу нужно обновить конфигурацию).

Фикстура `tool/setup_weak_ssh_fixture.sh start|stop` поднимает пять экземпляров sshd на 2231–2235: только SHA-1 обмен ключами, только CBC, только HMAC-SHA1, только ключ хоста ssh-rsa и контрольный «только современное» (curve25519, AES-GCM, hmac-sha2-256-etm, rsa-sha2-512). Тест `obsoleteAlgorithmsAreRefused` (`--weak-ssh` в `run_live_tests.py`): четыре слабых отвергаются до показа отпечатка, контрольный и обычный сервер подключаются. Регрессия: `fortiq_publication` 49, юнит-наборы, живые наборы `fortiq_ssh_it`; в полном прогоне осталось 3 красных теста из-за окружения (два требуют вход по паролю, `mailTlsConnections` — TLS-фикстуру почты). Попутно исправлена проверка `reliabilityInvariants`: при пустом пароле (запуск по ключу) она всегда была ложной.

**Не покрыто / риски:** серверы только с `ssh-rsa`/SHA-1 или CBC (старые сетевые устройства, CentOS 6) больше не подключаются — это решение, а не побочный эффект; если владельцу нужен режим совместимости, он должен быть явным и по серверу; клиентский вход по RSA-ключу (подпись пользователя) этой политикой не управляется; Android-сборка libssh2 и её список алгоритмов не проверялись (порядок и состав могут отличаться — проверить при квалификации); `libssh2_session_supported_algs` использует то, что собрано в библиотеке, поэтому состав зависит от бэкенда (OpenSSL / mbedTLS / wincng).

- **S-10a (P0, падение):** больше 16 параметров в CSI (`ESC[1;1;…;1m`) писали за границу массива `args[]`: приложение падало с нарушением доступа от одной строки вывода.

### Результат R14 (25.10.2026): libssh2 из master

- **Порт:** [`third_party/vcpkg-overlay-ports/libssh2`](../third_party/vcpkg-overlay-ports/libssh2/README.fortiq.md) — копия порта vcpkg 1.11.1#3, `REF` = коммит `6e7b2076a6ced2230968b27ee7c1abb77fe5a88d` (SHA-512 архива зафиксирован), патчи упаковки vcpkg убраны (к master не применяются; `find_package(libssh2 CONFIG)` работает). Версия в SBOM — `1.11.1-git6e7b207`, компонент опознаётся по коммиту, без CPE.
- **Пересборка:** Windows (`vcpkg install libssh2:x64-windows`, полная пересборка приложения) и Android arm64 (`libssh2:arm64-android`, `tool/build_android.py --package`). Копии прежних деревьев зависимостей остались вне репозитория как откат (`C:\Users\cybou\vcpkg-installed-backup-r14`, `android-deps-installed-backup-r14`).
- **Найдено при проверке (S-1 пригодился):** новый libssh2 по умолчанию согласует **другой тип ключа хоста** (раньше ECDSA, теперь Ed25519), отпечаток меняется, и **все сохранённые отпечатки пользователей превратились бы в тревогу «ключ хоста изменился»** (`fortiq_publication` упал с этим сообщением). Исправлено в `applyAlgorithmPolicy`: порядок ключей хоста задан явно (ECDSA, Ed25519, RSA/SHA-2) и не зависит от версии библиотеки; регрессию ловит проверка `obsoleteAlgorithmsAreRefused` (отпечаток обычного сервера равен закреплённому).
- **Проверено на Windows с новой библиотекой:** `run_live_tests.py` — `fortiq_publication` 49/49, все юнит-наборы, `fortiq_ssh_it` 44 прошли (было 42; 3 красных те же, что и раньше, из-за окружения: вход по паролю ×2, TLS-фикстура почты), ctest 18/18, S-1 (`obsoleteAlgorithmsAreRefused`), рукопожатие со всеми фикстурами.
- **Android (эмулятор FortiqTablet, 25.10.2026): проверено.** APK со статически собранным libssh2 `6e7b207` установлен через `tool/android_emulator_smoke.py` и запущен; сохранённый профиль `fqshell@127.0.0.1:2222` с отпечатком, **закреплённым ещё старой библиотекой**, прошёл проверку отпечатка (сообщение было «SSH authentication failed (private key)», а не «ключ хоста изменился») — то есть закрепления на Android пережили обновление; после указания одноразового ключа вход прошёл, в Fichiers открылся домашний каталог фикстуры (17 элементов, 13 папок, SFTP 531 мс). Касания через `adb input`, не пальцем; плюс прежние оговорки эмулятора ([PLATFORM_QUALIFICATION](PLATFORM_QUALIFICATION.md)). Ключ удалён с сервера и из каталога приложения.
- **Враждебный сервер:** `tests/fixtures/evil_ssh_server.py` + `maliciousServerCannotCrashTheClient` (23 варианта повреждённых пакетов до аутентификации, дважды; `run_live_tests.py` запускает сервер сам). **Честная оговорка:** старый libssh2 1.11.1 этот набор тоже переживает, то есть тест — регрессионная сетка, а **не воспроизведение CVE-2026-55200** (PoC требует особого содержимого, которого у меня нет).
