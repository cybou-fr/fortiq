# FORTIQ — подключение магазина Lemon Squeezy к Windows-клиенту

**Состояние:** базовый код покупки/активации подключён к приложению;
магазин, реальные товары и ссылки оплачиваемого checkout ещё должны быть
созданы владельцем аккаунта. В репозитории **нет** API-ключей Lemon Squeezy.

## Не путать лицензию с рабочим транспортом

FORTIQ — **frontend для серверных Linux CLI, запускаемых через SSH**.
Все предметные операции, включая почту, выполняются выбранным Linux-сервером
через SSH exec/PTY/SFTP/forwarding. **Прямого SMTP/IMAP из клиента нет.**
HTTPS-соединение с Lemon Squeezy служит только для покупки, лицензии
и управления подпиской до подключения к Linux и не меняет SSH-архитектуру
инструментов. См. [SSH_FRONTEND_CONTRACT](SSH_FRONTEND_CONTRACT.md).

## 1. Создать товары

В Lemon Squeezy (сначала в **Test Mode**) создать два товара:

| Товар | Цена для покупателя | Биллинг | Лицензия |
|---|---:|---|---|
| FORTIQ Intro | **2,00 €** | One-time | Generate license key; **14 days** |
| FORTIQ Pro | **39,90 € / год** | Subscription, ежегодное продление | Generate license key; срок определяется подпиской |

Для обоих товаров полный функционал одинаков. Intro не связан с пробным
периодом подписки и не вызывает автоматическое продление. Настроить
**tax-inclusive pricing**, проверить налоговключённую стоимость в checkout.
Промокоды, если понадобятся, ограничивать Pro, по умолчанию на первый платёж.

Подтвердить количество разрешённых активаций на ключ (пока решение не принято).
**Однократная покупка Intro на покупателя не обеспечена встроенной системой
лицензий**: нужен отдельный контролируемый механизм, если это строгое требование.

## 2. Какие публичные параметры скопировать из магазина

- **Store ID** (число).
- **Intro Variant ID** (число).
- **Pro Variant ID** (число, отличный от Intro).
- **Intro и Pro Checkout URL** (прямые HTTPS-ссылки магазина).
- **Store slug** (поддомен перед `lemonsqueezy.com`) для Customer Portal.

В клиент **не** добавляются:
- Lemon Squeezy API key (секрет продавца);
- webhook signing secret;
- customer portal signed/private URLs.

Ссылки checkout и числовые ID сами по себе не являются секретами.
Клиент сопоставляет `store_id` и `variant_id` с ответами лицензии.

## 3. Запуск и тестирование

Идентификаторы магазина (`store_id`, `variant_id`, ссылки checkout) передаются клиенту при сборке
(способ — параметры CMake или файл конфигурации; выбирается вместе с каркасом Qt-проекта).
Создать **локальный** `config/lemon_squeezy.local.json` по примеру
[lemon_squeezy.example.json](../config/lemon_squeezy.example.json); файл не коммитится.

Требования к поведению (из прототипа):

- Релизная сборка всегда требует лицензию; отладочная может включать экран активации флагом.
- Если не заданы корректные Store ID и Variant ID, показывается экран ошибки конфигурации.
- До публичного выпуска проверить, что ссылки и идентификаторы относятся к нужным тарифам.

## 4. Пользовательский сценарий

1. Приложение запускается **без SSH** и предлагает Intro / Pro.
2. Нажатие на тариф открывает штатный браузер и Lemon Squeezy Checkout.
3. После оплаты Lemon Squeezy отправляет покупателю ключ лицензии.
4. Покупатель вставляет ключ в FORTIQ.
5. Клиент по HTTPS вызывает License API `validate` (проверка продукта),
   затем `activate`, затем `validate` с `instance_id`.
6. После успешного ответа ключ и ID экземпляра сохраняются на Windows
   **зашифрованными с помощью DPAPI** (в контексте текущего пользователя).
7. При следующем запуске идёт новая онлайн-проверка; только после неё
   рабочий стол и SSH-инструменты становятся доступны.
8. Кнопка ключа в углу рабочего стола позволяет проверить статус, открыть
   Customer Portal для Pro и деактивировать текущий экземпляр.

Нет утверждённой offline grace policy: этот срез **не** даёт офлайн-доступ
на основе неподписанного локального времени. При отсутствии сети сохранённый
ключ остаётся на диске, но доступ требует повторить проверку.

## 5. Что протестировать перед реальными продажами

- Первый запуск, обе покупки в Test Mode, точные итоговые цены.
- One-time Intro: **14 дней**, отсутствие повторных списаний и перевода в Pro.
- Pro: ежегодное продление, отмена в Customer Portal и сохранение доступа
  до оплаченной даты.
- Правильный ключ и ключ от другого Store/Variant.
- Неверный, просроченный, отключённый ключ и исчерпанный activation limit.
- Повторный запуск, повторный ввод того же ключа, смена устройства,
  деактивация и повторная активация.
- Нет сети: данные пользователя сохранены, статус понятен.
- Windows DPAPI сохраняет ключ шифрованным; после смены пользователя
  доступ к его расшифровке отсутствует.
- Полная Windows-сборка, реальные SSH-сценарии, настройка Linux на VM.
- Отдельное решение для правила «Intro только один раз на покупателя».

## 6. Что надо реализовать в клиенте на Qt

Прежняя реализация (Flutter, Windows DPAPI, тесты, CI) удалена; её сценарии сохранены в теге
`flutter-final`. Новый клиент должен дать:

- службу лицензии: вызовы License API, проверка продукта и экземпляра, состояния и ошибки;
- экран выбора тарифа: два тарифа, checkout, активация, проверка и деактивация, Customer Portal;
- проверку доступа до создания SSH-интерфейса;
- защищённое хранение лицензии средствами ОС (Windows DPAPI / Credential Manager);
- автотесты состояний лицензии и активаций.

**Оставшиеся R0-задачи:** проверенный реальный магазин и Test Mode, однократность
Intro по покупателю (если требуется строго), безопасное хранение импортированных
SSH-ключей (отдельная задача), Windows-подпись/установщик, финальные интеграционные
проверки и политика офлайн-доступа.
