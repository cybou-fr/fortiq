# FORTIQ AI — серверная консольная команда `ai` на llama.cpp

**Статус: спецификация, НЕ реализовано (18.10.2026).** Серверная команда и окна клиента, созданные в прототипе на Flutter, удалены вместе с ним (тег `flutter-final`); код надо писать заново. В клиенте Qt R0.1 интеграции AI нет; разработка Files/Editor (R0) идёт раньше AI.
Выбран готовый llama.cpp, но реальную GGUF-модель и установщик не выбирали; релизные CPU, память и скорость до испытаний не обещаются. AI — опциональный R2/P2, не блокирует R0/R1 и коммерческий релиз.

## 1. Простая архитектура без сервера AI

```text
FORTIQ GUI: Explain / Diagnose / Suggest (только визуализация)
                       │
                   SSH exec + stdin/stdout
                       ▼
         Linux: команда `ai` (тонкий CLI-адаптер)
                       │
        llama.cpp: `llama-cli` / `llama cli`
                       │
              GGUF-модель, CPU-only
```

**Имя пользовательской команды — строго `ai`, не `fortiq-ai`.**
Она пригодна также для вызова из обычного терминала Linux.

- Выбран готовый **llama.cpp**: inference, токенизация и расчёты модели — исключительно Linux. Никакого собственного inference engine, клиентской LLM или копирования рабочих данных на Windows.
- В первом варианте используем **только процесс CLI по запросу**: без `llama-server`, фонового демона, постоянно загруженной модели, открытых TCP/HTTP API-портов, автозапуска при SSH-подключении.
- CLI-имя runtime зависит от зафиксированного релиза: стандартные бинарные сборки имеют `llama-cli`, у новых способов установки доступно `llama cli`. Обёртка `ai` делает один из вариантов выбранным **после проверки версии и фактической совместимости**, не полагается на устаревшие флаги.
- Все файлы GGUF, бинарник, настройки AI и CPU-вычисления находятся на выбранном Linux VPS. Для FORTIQ **единственный рабочий транспорт — SSH**.
- AI **объясняет и советует**, но не вызывает shell-команды по тексту ответа, не меняет конфигурации, не пишет файлы и не применяет `sudo`. Взаимодействия с Linux выполняют обычные сервисы FORTIQ по явному действию пользователя.
- Если CPU/память недостаточны, AI вообще не включается. Остальные приложения FORTIQ работают без ограничений; слабые VPS специально ради AI не рекомендуем.
- Будущие Windows-модель, внешние AI API, agent/tool calling и иные транспорты — не часть этого решения.

Это **точечное согласованное исключение** из принципа «не писать свои Linux-утилиты»: команда `ai` только объединяет проверенные вызовы уже существующего llama.cpp и нормализует вывод для GUI, а не создаёт отдельный backend.

## 2. Контракт `ai` (собственные подкоманды обёртки, не llama.cpp)

| Команда | Что делает | Изменяет систему? |
|---|---|---|
| `command -v ai` | Обнаруживает CLI без inference | Нет |
| `ai status --json` | Возвращает CPU/RAM/disk/cgroup, наличие binary/model, доступность и причину disabled | Нет |
| `ai setup --check --json` | Проверяет системные требования, архитектуру CPU, совместимость GGUF и нужные файлы | Нет |
| `ai setup` | После **отдельного согласия** устанавливает проверенный llama.cpp и выбранный GGUF на Linux | Да, только setup |
| `ai benchmark --json` | **Реализовано:** ручной ограниченный CPU-only прогон с временем холодного запуска и peak RSS Linux; **не** точное tokens/s или готовая оценка производительности | Только временная нагрузка |
| `ai ask --stdin --json` | Совет по вопросу и выделенным данным, принятым через SSH stdin | Нет |
| `ai explain --stdin --json` | Объясняет выбранный фрагмент Linux-лога/конфига | Нет |
| `ai cache status --json` | Статистика попаданий/промахов и использованного диска | Только чтение |
| `ai cache clear` | Очищает только кеш выбранного Linux-пользователя после явного действия | Да, только файлы кеша |

**Только оболочка `ai` предоставляет эти подкоманды**, llama.cpp не обязан их иметь. Ответ структурирован и версионирован. Пример статуса (иллюстрация, не реализовано):

```json
{
  "schema": "fortiq-ai-status/v1",
  "available": false,
  "reason": "insufficient_resources",
  "runtime": "llama.cpp",
  "model": null
}
```

Пример ответа (иллюстрация, не реализовано; поле `cached` добавляется при работе кеша):

```json
{
  "schema": "fortiq-ai-advice/v1",
  "status": "ok",
  "cached": false,
  "advice": "Проверить конфигурацию службы",
  "caution": "Совет модели не подтверждает результат проверки"
}
```

**Передача и приватность:** Клиент передаёт выбранный текст через SSH stdin; не помещать фрагменты логов и секреты в аргументы процесса, историю shell или логи. Нужно отдельно проверить на конкретной версии `llama-cli`, как надёжно предоставить stdin модели **без записи prompt на постоянный диск**: поддерживаемый stdin-режим или неперсистентный безопасный файловый дескриптор. Не утверждать, что `llama-cli` безусловно поддерживает `--stdin`. Если безопасный механизм не подтверждён, реализацию отложить.

Машинный JSON формируется и проверяется **обёрткой**. При желании использовать JSON-schema/grammar llama.cpp, но не доверять корректности структуры без валидации. Нужны exit code, отдельный stderr, лимит размера вывода, таймаут, отмена процесса и состояние `unknown` после разрыва SSH. Ответ LLM никогда не интерпретируется как shell-код.

## 3. CPU-only: политика запуска

**GPU не требуется и не предполагается.** Учитываются реальное `MemAvailable`, cgroup memory limit и pressure, загрузка CPU, число доступных vCPU, CPU-инструкции, свободный диск и состояние основных Linux-сервисов. Не считать установленную память гарантированно свободной.

- **1–2 ГБ RAM:** AI по умолчанию отключён. FORTIQ поддерживает основные инструменты как обычно.
- **4 ГБ RAM:** только кандидат на тест компактной модели; включать после измерения реальной свободной памяти, доступных CPU и скорости. Не обещать качество или работоспособность.
- **8 ГБ+ RAM:** тоже не гарантия разумной скорости на слабом/vCPU-throttled VPS.
- **Модель пока НЕ выбрана:** отобрать небольшие поддерживаемые **GGUF Q4** с разрешёнными условиями распространения и оценить на реальных CPU-only VPS. Сравнить пиковое потребление RAM (включая KV), first-token latency, tokens/s, загрузку CPU и деградацию других служб.
- Использовать опробованные CPU-only параметры выбранной версии llama.cpp: предел потоков, небольшой контекст, предел выводимых токенов, `--n-gpu-layers 0` если поддерживается. Настроить `nice`/systemd-run или cgroup для ограничений CPU/RAM при необходимости, **не создавать постоянно работающий AI-сервис**.
- Не запускать benchmark и не скачивать GGUF при обычном подключении/открытии окна. Модель загружается только по запросу и освобождается после завершения процесса. После некорректного завершения не оставлять дочерних inference-процессов.

Предполагается, что `ai benchmark --json` измеряет cold-start wall time, peak RSS и размер ответа; **порог «слишком медленно» и автоматическая CPU-квалификация нужно определить по замерам**. `ai status` отключает AI при нехватке памяти/модели/runtime, а GUI проверяет это **до сбора логов**. **Никакой блокировки стандартного FORTIQ** из-за необязательного AI.

## 4. Серверное кеширование вопрос → ответ (необязательная функция CLI)

**Цель:** повторный идентичный запрос возвращается непосредственно из кеша на
Linux **до запуска llama.cpp и загрузки GGUF**, экономя CPU/RAM и время.
Кеш принадлежит **серверу**, не клиенту; без отдельной БД на Windows,
сетевого порта, демона или внешнего сервиса. Реализуется лёгкой логикой
обёртки `ai`, независимо от нативного KV/prompt-cache llama.cpp.

**Первая версия: только точное совпадение**, никаких embeddings,
семантического поиска, «похожих вопросов», approximate matching или
дополнительной AI-модели для поиска по кешу. Ключ для нормализованного
запроса вычисляется криптографическим хешем из:

- версии схемы `ai`, системных инструкций и шаблона запроса;
- точной **версии и контрольной суммы GGUF**, параметров инференса
  (контекст, температура, seed, если задан, и ограничения генерации);
- типа операции (`ask` / `explain`), языка и содержимого запроса;
- точного содержимого **выбранного серверного контекста** (например,
  конкретного фрагмента journal), идентификатора ресурса/источника и
  версии контекста, если она есть.

Серверный контекст **не включается в ключ только по пути или ID службы**:
старые логи/изменившаяся конфигурация должны дать другой хеш. Путь
хранилища кеша выбирается в защищённом каталоге пользователя на Linux
(например, `~/.cache/ai/`), `0700` на каталоге и `0600` на записях,
с атомарной записью, контролем гонок и максимальным объёмом.

**Порядок одного вызова:** проверить вход/доступность и политику кеша →
рассчитать ключ → проверить TTL и метаданные → если hit, вернуть
версионированный JSON с `cached: true` **без запуска модели** →
иначе проверить CPU/RAM и запустить llama.cpp → проверить результат →
атомарно записать пригодный ответ → вернуть `cached: false`.
Сбой или переполнение кеша не блокируют обычное выполнение `ai`;
ошибки модели, timeout, неполные ответы и `unknown` **не кешировать**.
При отсутствии ресурсов для генерации можно вернуть **только свежий
подходящий кеш**, с пометкой `cached: true` и возрастом записи;
устаревший ответ не выдавать за актуальный.

**Свежесть:** отдельные TTL по типу вопроса; начальные значения для
пилота — **10 минут** для объяснения логов/состояния служб,
**24 часа** для общих объяснений. Это не универсальная истина:
TTL настраивается, при изменении данных/модели/prompt версия меняется и
запись больше не подходит. Результат — **совет**, не свежая проверка
`systemctl`; GUI показывает «из кеша», время создания и возраст.
Перед любым реальным действием Linux выполняется новая независимая проверка.

**Конфиденциальность:** кеш — новый слой долговременного хранения
потенциально чувствительных ответов. Для пользовательских логов,
конфигураций и иных чувствительных материалов **кеш отключён по умолчанию**,
пока пользователь не разрешил его явно. Общие несекретные вопросы могут
кешироваться по подтверждённой пользовательской настройке.
Для явно конфиденциального запроса предусмотрен `--no-cache`;
не записывать необработанные секреты, prompts или приватные ключи в
имена файлов, ключи кеша и логи. Хеш ключа сам по себе **не шифрует
содержимое ответа** — защита кеша `at rest` должна быть согласована с
будущей серверной политикой шифрования. До неё ясно показывать последствия
включения кеша, давать `ai cache clear` и ограничивать сроки хранения.
Кеш **строго изолирован на уровне Linux-пользователя и выбранного хоста**;
не переносить его между серверами или профилями SSH автоматически.

**Приёмка кеша:** повтор идентичного вопроса даёт hit без старта
`llama-cli`; изменение хотя бы одного важного поля ключа даёт miss;
TTL истёк → miss; тесты на параллельные запросы, атомарность,
права доступа, размер и очистку; чувствительный ввод не попадает в кеш
без разрешения. Замеры `hit rate`, latency hit/miss и расход CPU
проводим **на Linux** без передачи содержимого пользователю/в облако.

## 4. Установка, проверка и обновление

- Установка только с **явного согласия пользователя**, через SSH на Linux средствами существующего ServerSetupService; AI не входит в его обязательные шаги. Установка не требует клиента на Windows.
- Перед установкой проверить `command -v ai`: если имя уже занято другим инструментом, **не заменять чужой исполняемый файл**; определить безопасную политику установки/согласования до реализации.
- Использовать подписанный/контролируемый выпуск llama.cpp или воспроизводимую сборку CPU-only из закреплённого исходного commit/tag. Проверять SHA-256/происхождение артефактов, нужные версии glibc/CPU-инструкций, license. Сборка из исходников на слабом VPS может быть неоправданной: предпочесть подходящий предварительно проверенный бинарный пакет, если доступен.
- Проверить `llama-cli --version` или `llama --version` в зависимости от реально выбранного пакета, а также `--help` и повторяемость запуска. Не предполагать, что флаги одинаковы у всех выпусков.
- Размещение GGUF и исполняемых файлов, права на каталоги, quota, обновления и удаление AI описать отдельно; **все постоянные настройки хранятся на Linux**.
- Никаких автоматически запускаемых shell-скриптов неизвестного происхождения. Проверять модель и лицензию; не загружать удалённый GGUF по требованию необработанного текста пользователя.

### Техническая проверка runtime

Проверить в закреплённой версии CLI (не считать следующим примером гарантированный API):

```bash
llama-cli --version
llama-cli --help
llama-cli -m /path/to/verified-model.gguf --threads 2 --ctx-size 1024 --n-predict 128 --n-gpu-layers 0
```

Это **пример флагов для протокольного теста**, а не скрипт автоустановки и не обещание ресурсов/скорости. У официального проекта существуют `llama-cli` и/или новая форма `llama cli`; команда `ai` адаптирует только реально испытанный вариант.

Официальные источники: [llama.cpp](https://github.com/ggml-org/llama.cpp), [CLI](https://github.com/ggml-org/llama.cpp/blob/master/tools/cli/README.md), [Build](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).

## 6. Первое применение в GUI

**Будущая (не реализованная) функция: «Explain with AI» в Logs/Services.** На Qt R0.1 Logs ещё нет. После реализации [Logs](LOGS_INTELLIGENCE_SPEC.md) журнал будет читаться через SSH; только по отдельному согласию AI получит явно выделенный фрагмент через `ai explain --stdin --json`. В результате показываем объяснение, предположение и шаги ручной проверки.

Позже, после успешного CPU-пилота: Editor (объяснить выбранные строки конфига), Terminal (предложить команду, но не запускать). Не создаём обязательное AI-приложение и не читаем всю систему без явного запроса.

Логи и документы — недоверенные данные. Никаких инструкций из этих текстов в tool execution, никаких автоматических команд из LLM, никаких prompt/response history по умолчанию; секреты необходимо по возможности исключать из контекста.

## 7. Приёмка и границы

1. CPU-only Debian/Ubuntu VPS, малый и средний: измерены пик RAM, first-token latency, tokens/s, влияние на остальные службы; слишком слабый VPS получает корректный `disabled` без OOM.
2. `ai status` только читает состояние; `ai setup` требует явного разрешения, версия runtime/GGUF фиксируется.
3. Linux `ai` обрабатывает stdin, возвращает корректный JSON/error/exit code; работает без постоянного демона, TCP listener и клиента к внешнему API.
4. SSH-обрыв/timeout/cancel не оставляют runaway inference, не вызывают автоматический повтор или опасное действие.
5. Logs/Services работают даже когда нет модели или бинарника. Ответ AI остаётся советом, а не проверкой `systemctl` или `nginx -t`.
6. Повтор идентичного допустимого вопроса обслуживается серверным кешем без запуска GGUF; свежесть, TTL, изоляция, очистка и запрет хранения чувствительного ввода без согласия проверены тестами.
6. Оплачиваемый облачный inference не обещается.

**Релизный статус:** R2/P2, не реализовано. Нужны: выбор модели, испытание настоящего llama.cpp/GGUF на CPU VPS, безопасный установщик, серверная команда, окна клиента, интеграционные SSH-тесты. Не рекламировать AI как готовую функцию.
