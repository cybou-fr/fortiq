## 1. Базы данных

| Движок | Клиент на сервере | Debian 13 | Лицензия клиента | Формат вывода для GUI |
|---|---|---|---|---|
| SQLite (файл на сервере) | `sqlite3` | 3.46.1 | public domain | `-json` (нужен SQLite ≥ 3.33; Ubuntu 20.04 имеет 3.31 — без `-json`), иначе `-header -csv` |
| PostgreSQL | `psql` | 17 | PostgreSQL License | `--csv` + `-P null=<случайный маркер>`; JSON-обёртки не нужны |
| MariaDB/MySQL | `mariadb` / `mysql` | 11.8.6 | GPL-2.0 | `--xml` (единственный способ отличить NULL от строки «NULL»); `--batch` неоднозначен |

Проверенные факты (скрипты и их вывод сохранены в [docs/research/](research/): `research_db.sh`/`.out`, `research_db2.sh`/`.out`, `research_mail.sh`/`.out`; запускаются от root на одноразовом Debian):

- **psql `--csv`:** NULL и пустая строка в CSV выглядят одинаково; **`-P null='<<N-7f3a>>'`** делает NULL однозначным (маркер генерируется случайно на запрос и передаётся как данные). Многострочные значения и кавычки корректно экранируются.
  Несколько операторов в одном вводе выводятся последовательными таблицами (разбор нужен). Коды выхода: 1 — ошибка SQL, 2 — ошибка соединения; сообщения английские, с `LINE n:` и указателем.
- **psql, защита от записи:** `PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=5000'` блокирует `INSERT/CREATE` (`cannot execute … in a read-only transaction`), и таймаут срабатывает. **Но пользователь может выполнить `SET default_transaction_read_only=off`** —
  это защита от случайности, а не от злонамеренного SQL; настоящая защита — роль БД без прав записи. Установка `SET …` в том же `-c` как первый оператор **не** защищает (проверено: таблица создалась).
- **psql, размер:** 20000 строк по 200 байт = 4,8 МБ вывода; без ограничения вывод огромен. Универсальной подстановки `LIMIT` нет (DDL, несколько операторов): нужен потоковый предел на стороне клиента (закрыть канал при превышении) и явная пометка «усечено».
- **psql, интроспекция:** `information_schema.tables/columns` и `psql -l` дают схему; `ssl` включён по умолчанию. `PGCONNECT_TIMEOUT` работает; ошибка пароля: `FATAL: password authentication failed` (exit 2).
- **sqlite3 `-json`:** NULL → `null`, юникод корректен, `pragma table_info(t)` и `sqlite_master` дают схему. **BLOB в JSON портится** (проверено: `x'00ff10'` → мусор): BLOB надо оборачивать в `hex()`/`quote()`.
  `-readonly` отклоняет запись на уровне открытия файла (exit 8) — **это настоящая защита**; `pragma query_only=on` тоже. Ошибки: `Error: in prepare, near "selct": syntax error`.
- **mariadb `--xml`:** NULL представлен `xsi:nil="true"`; строки с табуляцией и переводами строк сохраняются; `--batch` печатает `NULL` и для NULL, и для строки «NULL» (неоднозначно). Защита от записи: `--init-command="SET SESSION TRANSACTION READ ONLY"` (ошибка 1792),
  таймаут: `SET STATEMENT max_statement_time=…` (ошибка 1969). Клиент **печатает текст запроса в stderr при ошибке** — запросы не логировать.
- **Секреты:** `PGPASSWORD`, `MYSQL_PWD` — переменные среды внутри скрипта на stdin (не аргументы, не в `ps`); `mariadb --defaults-extra-file` с временным файлом 0600 — запасной вариант.

**Рекомендация (на решение владельца):** приложение «Bases de données» на `sqlite3`, `psql`, `mariadb` (клиент на сервере; сам сервер БД может быть в другом месте): по умолчанию режим «только чтение» (опции выше + прямо сказано, что это не граница безопасности),
запись — отдельным явным подтверждением, лимит вывода и времени, схема слева, результат таблицей, выгрузка в Files. Учётные записи БД хранить так же, как SSH-секреты (защищённое хранилище клиента, метаданные в профиле).

Решения, которые нужны от вас: (а) какие движки в первом срезе (предлагаю SQLite + PostgreSQL), (б) где хранить профили подключений (клиент с защищённым хранилищем — как SSH, или на сервере), (в) допускать ли запись в первом срезе.

Проверенные факты `notmuch` 0.39: заголовки RFC 2047 декодируются (`Zoë Müller`, `Café au lait ✓`), `search --format=json` даёт тред, авторов, тему, время, теги; `show --format=json` даёт дерево MIME с `multipart/alternative` (text и html-части, имя файла, вложения);
теги меняются командой `notmuch tag`; запрос — данные (инъекция в строку запроса возвращает пустой результат, а не выполнение команды). HTML-часть нужно показывать нашим `HtmlSanitizer` (удаляет script/img/ресурсы), как в Browser.

**Рекомендация (на решение владельца):** композиция `mbsync` + `notmuch` + `msmtp`; GUI читает JSON `notmuch`, меняет теги, отправляет через `msmtp` (письмо передаётся по stdin, получатели — данные). Настройка аккаунта — мастер, который записывает `~/.mbsyncrc` и `~/.msmtprc` (0600) на сервере **только с вашего согласия** и показывает точное содержимое.
Пароли: `PassCmd`/`passwordeval` с `pass`/`secret-tool` не предполагаются на headless-сервере — нужен вариант хранения; это ваше решение (файл 0600 на сервере или менеджер).

Решения: (а) подходит ли композиция; (б) как хранить пароли почты на сервере; (в) первая версия только чтение + теги, отправка — вторым срезом?

## 3. Signal

Источник: [signal-cli, README](https://github.com/AsamK/signal-cli) и [wiki JSON-RPC](https://github.com/AsamK/signal-cli/wiki/JSON-RPC-service) (прочитаны 23.10.2026; сам инструмент не устанавливался и не запускался).

- **Лицензия:** GPL-3.0. Нет в стандартных репозиториях Debian 13 (`apt-cache policy signal-cli` — отсутствует); распространяется как архив с GitHub.
- **Требования:** README требует **Java 25 или новее**; в Debian 13 доступна Java 21 (`openjdk-21-jre-headless`) — **не подходит**. Нужна отдельная установка JRE 25 (вне apt) либо экспериментальная нативная сборка GraalVM. Нативные библиотеки libsignal включены для Linux x86_64 (нужна свежая glibc); другие платформы (например arm64-серверы) — отдельные шаги.
- **Режим для встраивания:** `signal-cli jsonRpc` читает JSON-RPC со stdin и пишет в stdout — **без порта и сокета**; это совпадает с нашей моделью «только SSH». Но требует **долгоживущего** канала (стрим), а не запроса-ответа: у клиента сейчас такой канал есть только в Terminal, для Signal нужна отдельная реализация.
- **Подключение аккаунта:** `signal-cli link` привязывает к существующему аккаунту (как дополнительное устройство; выводится ссылка, из которой клиент может нарисовать QR); `register`/`verify` — регистрация номера, возможна CAPTCHA, **регистрация снимает номер с других клиентов**. Лучше только привязка (link).
- **Хранение:** ключи и пароль в `~/.local/share/signal-cli/data/` на сервере; README не говорит о шифровании этих файлов — **любой, кто читает домашний каталог сервера, получает доступ к аккаунту**.
- **Сопровождение:** README предупреждает, что **релизы старше трёх месяцев могут перестать работать** (меняется сервер Signal) и что входящие сообщения нужно получать регулярно. Это постоянная обязанность по обновлению, а не разовая установка.

**Рекомендация (на решение владельца):** Signal — **после** баз данных и почты и только если вы принимаете: JRE 25 вне apt, ручные обновления раз в 1–3 месяца, ключи на сервере в открытом виде. Минимальный срез: привязка устройства (QR), список бесед, чтение и отправка текста.
