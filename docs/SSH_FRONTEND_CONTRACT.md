# FORTIQ — обязательный архитектурный контракт SSH / CLI

**СТАТУС: ОБЯЗАТЕЛЬНО (normative). Применяется ко всему текущему коду, будущим приложениям, roadmap и публичным обещаниям.**  
**Дата решения:** 2026-10-11. **Ответственный документ:** этот файл. При расхождениях остальные документы и реализации приводятся к нему.

## 1. Непересматриваемая модель продукта

**FORTIQ — Distributed Desktop Software, тонкий графический frontend для командных утилит на Linux-сервере.**

- **FORTIQ (Flutter/Qt/WebView/UI)** отображает окна, формы, результаты, прогресс, настройки, выбирает сервер и передаёт команды. Не реализует альтернативный локальный движок рабочих приложений.
- **Все предметные действия над рабочими ресурсами выполняются на выбранном Linux-сервере**: либо стандартной CLI-командой, либо существующей сторонней серверной CLI-утилитой, либо утилитой FORTIQ, которую мы разрабатываем, поставляем и запускаем на сервере.
- **Единственный прикладной транспорт между FORTIQ и Linux — SSH**: команды через SSH exec/shell/PTy и потоковый stdin/stdout/stderr; файлы — SSH exec и/или SFTP (это подсистема SSH); проброс портов — только SSH forwarding. Серверный CLI может сам обращаться к локальным файлам, системным демонам, внешним сетевым сервисам и почтовым провайдерам.
- **Нет самостоятельных клиентских соединений с ресурсами**: Flutter не открывает SMTP, IMAP, POP3, FTP, WebDAV, прямые HTTP(S) API удалённого ПО, системные daemon socket или TCP-порты для обхода SSH.
- **Не нужен постоянно работающий агент или отдельный HTTP/REST/RPC-сервер на Linux**. При нехватке возможностей пишем **CLI-команду**, запускаемую через SSH; при необходимости у неё может быть отдельный краткоживущий процесс. Постоянная служба — только по отдельному явному архитектурному решению, не подразумевается.
- Ни одно окно не считается готовым только потому, что Flutter-виджет существует. У каждого инструмента обязателен описанный и проверенный **серверный исполнитель**.

**Исключение только для управления самим продуктом:** локальный GUI/настройки/хранилище SSH-ключей, локальная черновая копия для предотвращения потерь, покупка и проверка лицензии Lemon Squeezy (HTTPS) и обновление клиентского приложения. Это *control plane FORTIQ*, а не доступ к рабочим ресурсам. Кеш/черновик не превращается в самостоятельную локальную рабочую версию приложения и не становится авторитетным источником серверных данных.

## 2. Обязательное правило добавления любого инструмента

Каждое `APP-xx` и каждое новое действие описывается в **карточке CLI-контракта**:

1. **Linux-подсистема и CLI-исполнитель:** точная команда/пакет либо имя создаваемой `fortiq-*` утилиты. Без исполнителя feature откладывается.
2. **Способ доставки:** установлен в Debian/Ubuntu; устанавливается через `apt` по SSH; или поставляется/обновляется FORTIQ через SSH с проверкой версии/целостности.
3. **Capability check:** `command -v`, обнаружение версии, необходимых прав и supported flags. Ошибка отсутствующей возможности отображается явно.
4. **Протокол запуска:** SSH exec для конечного запроса, PTY для терминала, stdin/stdout/stderr для потоков; SFTP для файлов, SSH forwarding для туннеля. Ни одного прямого клиентского транспорта.
5. **Машинно-читаемый результат** там, где это нужно: версионированный JSON Lines/JSON/разделители с проверкой статуса завершения. Не разбирать локализованный человекочитаемый текст там, где доступен стабильный формат.
6. **Права, безопасность и ошибка:** минимальные привилегии, экранирование аргументов/передача через stdin, таймаут, лимит вывода, отмена, `unknown` после обрыва при изменении данных, отсутствие секретов в логах.
7. **Тест:** FakeShell/unit → SSH integration → disposable Debian/Ubuntu VM при любых изменениях системы → UI-приёмка.

**Политика отсутствующих инструментов:** capability discovery → безопасная установка/обновление нужной серверной CLI-зависимости через имеющийся `ServerSetupService` → проверка версии и результата → предоставление инструмента. Не переносить вычисление на клиент и не вводить прямой сетевой fallback, если на сервере нет команды.

| APP-10 | Services | `systemctl`, `systemd-analyze` | SSH exec | Реализована основа |

Команды, которых пока нет в коде, указаны как **целевой выбор**, а не обещание реализации. Любой собственный `fortiq-*` бинарник/скрипт — **серверный CLI**, а не сервис с API. Все инструменты работают в контексте конкретного SSH-хоста; смена активного хоста никогда не перенаправляет уже начатую операцию.

### Browser: точная граница

Для интерактивной web-страницы WebView2 лишь **отрисовывает** контент в UI. Его запросы проходят через локальный SOCKS listener, который создаётся SSH forwarding; исходящий доступ к ресурсам выполняется со стороны выбранного SSH-сервера. `sshd` — серверный исполнитель этой функции на уровне транспортного протокола; для собственно CLI-функций анализа страниц/загрузок нужен `curl` или иной серверный CLI.

Нет fallback на прямой интернет клиента, в том числе для DNS/WebRTC/loopback. Поддержка браузера не объявляется полностью проверенной, пока этот маршрут не испытан end-to-end. Прямое обращение UI к удалённому HTTP — архитектурное нарушение.

## 4. Mail: строго серверный исполнитель

**Flutter FORTIQ никогда не работает с SMTP/IMAP/POP3 напрямую.**

Для Mail UI существует только `MailService → RemoteShell/SSH → mail CLI на Linux`. Возможные серверные реализации:
- **Системная почта:** читать серверный mbox/maildir консольными утилитами; отправлять через `mail` или `sendmail`. Если нет MTA, нельзя изображать успешную отправку простым добавлением записи в mbox.
- **Нормальные пользовательские ящики и MIME:** найти существующую надёжную консольную программу, способную работать с mailbox, папками, вложениями, отправкой и синхронизацией; либо реализовать `fortiq-mail` как **серверную CLI-утилиту** с версионированными командами (`list/read/send/reply/save-draft/attach/status`). FORTIQ вызывает её через SSH.
- Серверная утилита может *внутри Linux* использовать необходимый протокол к реальному почтовому поставщику или местную очередь MTA; **этим соединением управляет Linux**, никогда Flutter.
- Если SSH отсутствует, Mail показывает отключённый сервер и не выполняет операции чтения/отправки/синхронизации; допускается лишь UI и безопасно сохранённый временный черновик, который отправится **только после явного подтверждения** после переподключения.
- Отправка — изменяющая операция: при потере SSH результат **unknown** до подтверждения через серверный CLI; повторно отправлять вслепую нельзя.
- Хранение учётных данных для почтового сервиса происходит по согласованной политике безопасного серверного исполнения, без утечки токенов в argv, stdout, диагностику или пользовательские логи.

**Прямой SMTP/IMAP клиент и самостоятельная Mail Account adapter в Flutter удаляются из roadmap.** Если бизнес-задача требует почтовый аккаунт, это **Mail CLI capability выбранного Linux-хоста**, а не дополнительный клиентский транспорт.

## 5. Что локально, а что удалённо

**Локально в FORTIQ:** визуальная оболочка, окна, диалоги, изображение результатов в памяти, временная защищённая копия несохранённых правок, профили серверов и учётные данные SSH, настройки UI, ключ лицензии и покупка через Lemon Squeezy.

**Удалённо на Linux:** все рабочие файлы, документы и редактируемые ресурсы как первоисточник; поиск, письмо и mailbox, системные службы/сеть/диски, диагностические команды, серверный рендеринг/конвертация по потребности, загрузки, внешние аккаунты и их взаимодействия.

Несколько серверов = несколько независимых SSH-сессий. «Account» означает аккаунт **серверной CLI-утилиты** и всегда привязан к `serverId`, но не прямое сетевое подключение из клиента. Пользовательские действия по ресурсам без SSH не выполняются. В офлайне разрешены только UI, лицензирование, отображение последнего статуса (явно устаревшего) и защита несохранённой работы.

## 6. Архитектурные проверки и запреты в review

- Каждое приложение в матрице имеет серверную команду/capability, тест CLI и SSH.
- Нет новых прямых `Socket`, `HttpClient`, IMAP, SMTP, FTP, внешних service SDK внутри рабочих `lib/services/*` и виджетов. **Явные исключения:** `license_service.dart` и проверенные обновления продукта — отдельный control plane.
- Если есть HTTP(S) внутри Browser, оно обязательно идёт внутри SSH forwarding и не падает обратно на клиентский direct route.
- Клиентская сеть должна работать по схеме **client → SSH → Linux CLI → target**; не **client → target**.
- Для новой функции 먼저 выбрать/написать CLI, оформить discovery/deploy/update/test; только после этого строить UI.
- Отсутствие SSH оставляет интерфейс управления соединением/лицензией, но отключает все предметные действия. Ошибка соединения не заменяется локальной операцией.
- Рабочий контекст всегда включает server ID, epoch и версию результата.
- Любая несогласованность с этим контрактом считается **блокирующей** для реализации и релиза.
